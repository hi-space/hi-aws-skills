# 한빛페이 워크숍 청사진 페르소나 리뷰 통합본 (persona-review.md)

먼저 짚어야 할 게 있습니다. 요청하신 "6인 평가"인데, 실제로 받은 데이터는 **5인분**입니다(L200/개발자, L200/데이터·ML, L200/아키텍트, L300/아키텍트, L300/데이터·ML). brief.yaml의 audience(role 3종 × level 2종 = 6페르소나) 기준으로 보면 **L300/개발자 페르소나 평가가 빠져 있습니다**. 아래 통합 결과는 이 5인분을 기준으로 한 것이고, L300/개발자 관점(예: "정산 배치 개발자가 보안 조사 씬을 얼마나 따라갈 수 있는가")은 별도로 채워야 빈틈이 남지 않습니다.

## 3. Blocker·Major 청사진 수정지시 (구체)

여기서는 "무엇을 어떻게 바꿔야 하는지"를 실행 가능한 단위로 풀었습니다. 위 표의 번호를 그대로 참조합니다.

**#1 벡터스토어를 지금 확정한다.** 지금 이 결정을 미루면 씬 대본·데이터셋 표·캡처 슬롯이 이미 "사전 인제스트 완료" 전제로 짜여 있는데, 뒤늦게 "참가자가 직접 인제스트한다"로 바뀌면 그 세 가지를 전부 다시 써야 합니다. 워크숍이 2026-09-15이고 3주가 안 남았으니, 세팅 공수가 가장 가벼운 쪽(서버리스라 사전 프로비저닝이 필요 없는 OpenSearch Serverless, 또는 그보다 더 가벼운 Aurora pgvector) 중 하나로 지금 정하고, 확정 즉시 PRE 씬 대본에 "발표자가 대량 문서는 미리 인제스트해 두었고, business_rules.md 1개 문서는 참가자가 실습 시작 직후 직접 업로드→인제스트→조회해 본다"는 문장을 못박습니다. 대가는, 이 마이크로 스텝을 넣으면 Scene 2 앞에 3~5분이 추가된다는 것입니다.

**#2 이상탐지 로직을 z-score 또는 이동평균 중 하나로 확정하고, 그 계산식과 임계값을 화면에 노출한다.** 참가자에게 "왜 이게 이상으로 잡혔는지"를 보여주지 못하면 시나리오 A 전체의 신뢰가 흔들립니다. Code Interpreter가 실제로 실행한 코드 셀과 임계값 숫자를 결과 카드 옆에 그대로 띄우는 스텝을 Scene 1 산출물에 추가합니다.

**#3 transactions_sample.csv 데이터 스펙에 시계열 보존 조건을 못박는다.** "가맹점·카테고리별 최소 30~60일 연속 일별 집계, 날짜·가맹점 단위로 시계열을 보존하는 다운샘플"이라는 문장을 4절 데이터셋 표에 그대로 추가합니다. 이걸 지금 안 정하면 데이터를 다 만든 뒤에야 "기준선이 없어서 이상탐지가 성립 안 된다"는 걸 발견하게 됩니다.

**#4 Policy 승인 게이트의 before/after 캡처 두 장을 확보 계획에 넣는다.** 승인 UI를 새로 만들 시간이 없다면 최소한 (1) 승인 없이 호출 시 거부 응답 화면, (2) 승인 후 성공 화면, 이 두 장을 5절 캡처 슬롯 목록에 명시적으로 추가합니다. 이게 없으면 시나리오 B의 정점 씬이 "주장"으로만 남습니다.

**#5 Scene 3(A)을 3a/3b로 쪼갠다.** Gateway+Identity(내부 mock API 조회)와 Browser(외부 공개 페이지 확인)를 순차 도입 순서로 배치하고, 진입 직전에 비유 문장을 필수 삽입합니다. 대가는 씬 하나가 둘로 늘어나 전체 90분 타임라인에 몇 분이 추가된다는 것이니, 다른 씬에서 시간을 줄일지 검토가 필요합니다.

**#6 핵심 용어 3개(이상탐지·RAG·Identity 스코프)의 "한 문장 쉬운 설명"을 지금 확정해 발표자 노트와 features 페이지에 동일 문구로 박는다.** 두 자료가 다른 설명을 하면 참가자가 혼란스러워지므로, 문구를 하나로 통일하는 게 핵심입니다.

**#7 Evaluations의 채점 대상 데이터셋을 past_anomaly_cases.json과 분리해 evaluation_labeled_set으로 새로 정의하고, 그중 5~8건을 Scene 1 삽입 이상치와 겹치게 설계한다.** 이 작업은 데이터셋 설계 담당자의 추가 공수가 들지만, 안 하면 Scene 5가 "정답 맞추기 슬라이드"로 전락합니다.

**#8 D1·D4 범례를 3단계로 재설계하고, Evaluations 사용 씬 발표자 노트에 리전 각주를 넣는다.** 이건 사실 확인이 끝난 항목이라 SA 판단 없이 바로 반영 가능합니다.

**#9 features 페이지마다 "이 서비스가 없으면 어떻게 되는가" 문단을 필수 항목으로 추가한다.** 특히 Gateway·Identity·Policy 3개는 발표자가 즉답할 수 있도록 노트에 미리 답을 적어 둡니다.

**#10 B PRE에 "1분 리캡" 슬라이드를 추가한다.** B만 듣는 L300 참가자가 실제로 있을 가능성이 A를 다 들은 참가자보다 오히려 높다는 점(brief.yaml audience 구조상)을 감안하면, 이건 선택이 아니라 필수로 봐야 합니다.

**#11 D5 또는 B PRE 발표자 노트에 "이 워크숍의 통제 범위는 사고 이후 에이전트 권한 통제이며 SSRF 자체 예방은 범위 밖"이라는 경계 문장을 명시한다.**

**#12 데이터 준비 단계에 "이상치-임계값 사전 검증" 체크포인트를 추가한다.** 삽입 이상치를 실제 로직 초안으로 미리 돌려보는 검증 단계이며, 이건 데이터 제작자와 로직 담당자가 같은 사람이 아니라면 반드시 리뷰 단계로 넣어야 합니다.

## 4. L200 쉬움 vs L300 어려움 긴장 해소

지금 청사진의 구조는 A(L200)가 "탐지→원인→사실확인→보고→검증"을 부드럽게 밟아가면서 AgentCore 기능을 하나씩 얹고, B(L300)는 같은 기능 팔레트를 재사용하되 처음부터 한 단계 높게 시작하는 방식입니다. 문제는 이 설계가 **"A를 먼저 듣고 B로 넘어가는 참가자"를 전제**로 하고 있는데, brief.yaml의 audience 구조(L200/L300이 같은 90분 세션에 섞여 있고, primary가 L200)를 보면 실제로는 L300 참가자가 A를 건너뛰고 B로 바로 들어갈 가능성이 낮지 않다는 점입니다. 그러면 B PRE부터 Gateway·Identity·Policy를 아무 배경 설명 없이 만나게 되어, 청사진이 스스로 세운 "인접 씬끼리 1단계 이상 벌어지지 않게 배치"라는 원칙이 시나리오 경계를 넘는 순간 깨집니다. 반대 방향의 문제도 있습니다. L300 아키텍트·데이터·ML 참가자 입장에서는 A와 B가 같은 서비스 조합을 재사용하는 구조라 "이미 아는 도구를 다시 보여준다"는 느낌을 받을 수 있고, 이들이 원하는 더 깊은 검증(정책 JSON 직접 보기, 리전 라우팅 확인 등)은 지금 어느 씬에도 없습니다.

이 긴장을 하나의 정답으로 없앨 수는 없고, 실제로는 참가자군을 쪼개는 쪽이 정직한 해법입니다. 아래처럼 진입 트랙과 심화 옵션을 나누는 걸 권합니다.

| 구분 | 대상 | 처리 방식 | 비용 |
|---|---|---|---|
| 진입 트랙 리캡 | B로 바로 들어가는 L300(AgentCore 처음 접하는 경우) | B PRE에 "핵심개념 1분 리캡" 슬라이드(Gateway=창구, Identity=출입증, Policy=승인게이트 3줄 비유) 고정 삽입 + A의 해당 features 페이지 링크 배치 | 발표자 노트 3줄 추가, 시간 1~2분 |
| 심화 옵션 스텝(스트레치) | A/B 모두 들었거나 이미 AgentCore에 익숙한 L300 아키텍트·데이터·ML | 필수 흐름과 별도로 "더 보고 싶다면" 옵션 스텝 추가 — 예: B Scene3에서 Identity가 발급한 실제 스코프 토큰 클레임을 콘솔에서 직접 열어보기, B Scene4에서 Policy의 Cedar 정책 JSON을 직접 읽어보기, A Scene5에서 evaluation_labeled_set의 정오분류표(confusion matrix)를 직접 계산해보기 | 90분 핵심 타임라인에는 넣지 않고 "시간이 남으면" 카드로 별도 배치 |
| 난이도 완충 분기 | A Scene3(신규 개념 3개 동시 등장)을 처음 겪는 L200 | 3a(Gateway+Identity)/3b(Browser)로 순차 분리 — L300에게는 굳이 다시 나누지 않고 그대로 통과시켜도 됨(이미 B에서 한 번 본 개념이라 재분리가 오히려 지루할 수 있음) | 씬 하나가 둘로 늘어남, 시간 배분 재조정 필요 |

핵심은, L200에게는 "쪼개서 천천히", L300에게는 "필수 흐름은 그대로 두고 옵션으로 깊이를 더한다"는 방향입니다. 옵션 스텝을 필수 타임라인에 넣지 않는 이유는, 90분이라는 시간 제약 안에서 L300용 심화를 강제로 끼워 넣으면 L200 primary 대상 참가자가 오히려 그 시간에 밀려나기 때문입니다. 대가는 명확합니다 — 심화 옵션은 "시간이 남는 조에서만 나온다"는 뜻이라, 모든 L300 참가자가 심화 경험을 보장받지는 못합니다.

## 5. 남은 열린 질문

청사진 7절의 원래 8개 열린 질문 중 4개는 이번 리뷰로 "결정 안 하면 자산 제작이 막히는 blocker"로 승격됐습니다(위 3절 #1·#2·#4, 그리고 채점기준 #7). 나머지는 여전히 SA/기획 판단이 필요한 상태로 남아 있고, 이번 리뷰에서 새로 드러난 질문도 있습니다.

| 질문 | 상태 | 비고 |

| 클래식 Guardrails 본체의 서울 독립 가용성 | 열림 (원 청사진 유지) | 시나리오 B 보조 통제로 얹을 수 있는지 별도 확인 대상 |
| 클래식 KB 벡터스토어 선택 | **닫힘 요구(blocker로 승격)** | 3절 #1 참조 — 지금 확정해야 함 |
| Code Interpreter 이상탐지 로직 수준 | **닫힘 요구(blocker로 승격)** | 3절 #2 참조 — z-score/이동평균으로 최소 확정 |

| **(신규) Evaluations의 글로벌 CRIS 라우팅을 어떻게 처리할지** | 신규 열림 | 이번 데모는 합성 데이터라 문제없다고 넘길지, 커스텀 evaluator로 우회할지 SA 판단 필요 |

**정리하면**, 이번 리뷰가 가장 강하게 요구하는 것은 "청사진이 열어둔 미결정 4개(벡터스토어·이상탐지 로직·채점기준·승인게이트 시연)를 지금 닫으라"는 것입니다. 이 4개를 닫지 않으면 이미 확정된 것처럼 쓰여 있는 씬 대본·데이터셋·캡처 슬롯이 나중에 통째로 재작업될 위험이 있고, 워크숍까지 3주가 안 남은 시점에서는 그 재작업 리스크가 가장 큰 비용입니다.

# 부록 · 페르소나별 원본 findings

## L200/개발자 — 완주: with_struggle

> 핵심 흐름(탐지→원인→사실확인→보고)은 개발자가 따라갈 만하지만, Scene 3에서 신규 개념 3개가 한꺼번에 쏟아지고 SA용 약어가 그대로 참가자 앞에 나올 위험이 있어 중간에 막힐 가능성이 큼.

- **[major·난이도점프]** 시나리오 A Scene 3 (사실 확인): Scene 2(RAG, ★★)까지는 '검색해서 찾아본다'는 익숙한 감각으로 따라올 수 있는데, Scene 3(★★★)에서는 Browser·Gateway·Identity라는 처음 보는 개념 세 개가 동시에 등장한다. 특히 '스코프된 자격증명으로 mock API를 조회한다'는 문장은 이게 OAuth 스코프인지, IAM 롤인지, API 키인지 아무 설명이 없어서 에이전트를 처음 쓰는 결제사 백엔드 개발자는 '내가 지금 뭘 발급받아서 뭘 하는 건지' 감을 못 잡고 그 자리에서 멈추기 쉽다. 다른 씬들은 한 씬에 새 개념 1~2개인데 이 씬만 3개가 겹친다.
  - fix: Scene 3을 쪼개서 Browser(사실확인)을 먼저 단독으로 실습하게 하고, Gateway+Identity(내부 API 조회)는 별도 스텝으로 분리한다. 또는 Scene 3 진입 직전에 'Gateway=도구를 안전하게 꺼내주는 창구, Identity=그 창구를 통과할 때 잠깐 쓰는 출입증'처럼 코드 비유 없이도 이해되는 한 문장 비유를 먼저 배치한다.
- **[major·용어]** 청사진 전제문 및 7절 열린 질문 (크로스리전 추론 프로파일, 클래식 KB vs Managed KB, Guardrails-in-Policy): '크로스리전 추론 프로파일', '클래식 KB', 'Guardrails-in-Policy' 같은 표현은 SA가 리전 가용성을 따질 때 쓰는 용어이지, 에이전트를 처음 접하는 개발자가 실습 중에 보고 이해할 수 있는 말이 아니다. 지금 청사진 상에서는 이 구분이 D5 다이어그램(왜 Guardrails가 없는가)에서만 해소되는데, 참가자는 Scene 진행 중에 이 용어를 먼저 마주친다. '클래식 KB'라는 표현도 '구식'이라는 뉘앙스만 주고 무엇의 구식인지(AgentCore 네이티브 KB와 API가 다르다는 것) 설명이 없다.
  - fix: 참가자용 자료에서는 '클래식 KB' 대신 처음 등장할 때마다 'Bedrock Knowledge Bases (에이전트 전용 신형 KB가 아닌 기존 방식)'처럼 괄호 설명을 매번 붙이고, '왜 Guardrails가 없는가' 답변은 D5를 보여주는 시점이 아니라 PRE/오리엔테이션 단계에서 한 문장으로 먼저 못박아 궁금증이 씬 중간에 터지지 않게 한다.
